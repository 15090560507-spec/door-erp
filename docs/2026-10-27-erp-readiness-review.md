# 经营管理与 ERP 上线检查

日期：2026-10-27。范围：当前仓库的订单确认、门樘履约、BOM、采购库存、人员工资代码及隔离测试。没有登录腾讯云读取生产日志，也没有进行公网渗透测试，因此不能把本文当成完整安全审计或生产验收证书。

## 结论

目前已具备门业生产协同系统的主体链路，可以作为公司业务 ERP 的基础继续建设、限制范围试点；尚不适合作为财务放行、工资审批和库存责任的唯一依据。优先补权限、审批、状态口径及可恢复性，再扩大使用范围，不建议先增加更多菜单。

已有优点：销售订单关联独立门樘；BOM 有版本冻结与变更；履约生成有幂等键和失败重试；库存有领退料与库位流水；质检、入库、发货存在后端状态检查；计件金额已有按分分配的实现。不能把它简单说成“没有逻辑”，但部分试运行规则需要升级为正式内控。

## 本轮已修复的加载与定位问题

1. 订单列表原先等待指标、待下达任务、人员等全部请求完成才显示。现拆开加载，不再被慢指标阻塞。
2. 搜索每个字符重载整页数据。现 250ms 防抖，只刷新订单列表；旧搜索响应不覆盖新结果。
3. 订单与首樘门详情原先两次串行 HTTP 请求。现提供兼容旧接口的合并响应，并即时切换选中反馈。
4. 列表传输完整 task_snapshot_json。现 SQL 只选择摘要字段；合并详情也不发送未使用的原始任务快照。旧详情接口仍可获取原始快照。
5. 详情对每个工序单独读依赖、反复建立连接。现批量读依赖，并在一次门樘详情读取内复用连接，显式关闭连接。
6. 内嵌 BOM 原先从全局前 100 条门樘中选择，当前门不在其中可能被替换成其他门。现严格绑定传入的门樘 ID，不加载全局列表。
7. 订单/门樘响应缺少竞争保护。现只接受最近选择；页面内缓存最多 20 项、15 秒失效，不持久化，刷新及本地写操作后清空。其他终端的变更最多可能有该短暂读取延迟，最终写入仍由服务端校验。

隔离的 30 工序读取样本：55 次连接降到 2 次；同机单次约 49ms 降到约 3.3ms。此值不是腾讯云端到端耗时，也不意味着所有页面都快 15 倍。云端最终速度仍需部署后结合接口耗时、响应大小、磁盘和网络确认。

## 待整改风险：按优先级排序

### P1：岗位权限目前没有真正隔离

证据：backend/auth.py:28 的 user_permissions 对所有用户返回全部生产权限。fulfillment_routes、inventory_routes、sales_order_routes、operations_routes 中大量写接口仅依赖 get_current_user。工资和客户收款等敏感资料也未形成按岗位、按数据范围的后端限制。

影响：登录不等于有权审批、收款、调整库存或查看工资。当前属于试运行的全开放策略，正式公司 ERP 中会成为越权风险。另一个相反的问题是 backend/bom_routes.py:27 写死仅账号 A 可访问，合法技术负责人或管理员未必能处理 BOM。

建议：建立销售、技术、采购、仓库、车间、质检、财务、主管权限矩阵；读和写分别授权，后端逐请求验证，默认拒绝；账号 A 的特例换成明确权限，不能只隐藏菜单。依据：[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

### P1：欠款发货的“授权”可由输入文字代替

证据：backend/fulfillment_database.py 的 create_shipment 用 authorization_reason 与 authorized_by 非空判断 authorized；backend/fulfillment_routes.py 的发货接口没有额外验证授权人身份或批准记录。

隔离复现：以普通录入员身份，给准备为已入库的测试门樘设置订单欠款 1000 元，填写任意授权姓名和原因，即得到 authorized=1 的发货记录。没有操作真实订单。

建议：放行申请与审批分离，授权人从登录身份获取，申请人不能自行填写任意姓名完成批准；批准记录绑定订单、欠款金额、有效期和审批人，出库时重新校验。

### P1：已审批工资仍可改，锁定可直接退回草稿

证据：backend/operations_routes.py:400 仅阻止“已锁定”明细修改，未阻止“已审批”；:424 的状态转换允许“已锁定→草稿”，且仅检查登录，没有解锁审批权限或理由。

隔离复现：普通录入账号修改已审批工资补贴，HTTP 200；同账号将锁定期间改为草稿，也返回 200。现有工资流程测试也使用普通录入员完成全部状态流转。

建议：已审批数据冻结；修改先撤销审批并记录理由，变更后必须重审；解锁只允许指定主管，保留原始金额、差额、理由和操作者审计。

### P2：进度、存储状态、五阶段状态不是同一个口径

证据：frontend/src/app/production/page.tsx 的左侧取订单聚合 progress/status；右侧取 build_fulfillment_workflow 重新推导的阶段；工序进度来自 WorkPackageService.refresh_progress。五阶段会检查是否发布算料，旧订单却可能已有“待成品质检/100%”状态。

影响：会出现用户截图里的“100% 但算料尚未开始”。这是口径或历史数据兼容问题，不应通过假填算料或直接修改进度掩盖。

建议：明确“工序完成率”和“整单履约阶段”两个字段；列表和详情共用统一阶段服务；对历史门樘提供受控补录/豁免流程，保留原因。算料阶段测试中仍有一项期待旧阶段名，已确认原版本同样失败，不能将当前测试全通过作为上线依据。

### P2：部分列表和记录仍有隐含上限

证据：backend/sales_order_database.py:541 默认 limit=100，sales_order_routes.py 的列表入口未提供分页参数并直接调用该默认值；返回 total 是已返回数组长度。门樘全部记录读取 fulfillment_events 时也 LIMIT 100，没有历史翻页入口。

影响：旧销售单或第 101 条以前的记录可能看不到。这是读取上限，不等于数据已删除。

建议：服务端分页、真实总数、可检索所有记录、历史记录游标；不要用一次把所有数据塞进浏览器的方式替代分页，也不能静默截断。

### P2：跨存储一致性与恢复流程仍需正式验收

证据：任务和报价使用 JSON，订单、履约等使用 SQLite。TaskDatabaseManager 使用进程内 threading.Lock，读取异常返回空数组；确认订单后更新任务状态的部分异常被忽略。SalesOrderFulfillmentService 已提供幂等生成与失败重试，这是优点，但不能等同于跨存储原子事务。

风险：开启多个写入进程后，进程内锁不能防止 JSON 的并发覆盖；文件读坏也不应被当成“没有任务”。当前未复现真实数据丢失，不应宣称已经丢单。

建议：读取失败明确报警、禁止继续覆盖；统一关键交易存储或提供可靠事件/对账补偿；先验证单实例稳定性，再评估是否迁移 PostgreSQL。SQLite 本身不自动意味着不能做小规模 ERP。备份要覆盖数据库、附件和配置，保留受控周期并做恢复演练；在线 SQLite 可采用官方一致性备份接口，不能只凭备份文件存在判断可恢复。依据：[SQLite Online Backup](https://www.sqlite.org/backup.html)。

### P2：小屏布局仍有横向溢出

证据：保留现布局的 390px 浏览器回归，记录到约 209px 横向溢出。桌面已检查截图，本轮按约定没有重排页面。

建议：手机端采用订单列表→门樘详情逐级进入；表格局部横向滚动，不让整页变宽。嵌套页面重复标题、空白区域和宽侧栏可在后续 UI 批次统一处理。

## 建议的公司 ERP 上下级关系

以销售订单为商业主单，以独立生产编号为执行主线：

销售订单/变更与收款计划 → 门樘生产单 → 已冻结 BOM/工艺版本 → 物料需求 → 采购/库存预留 → 到货检验/入库 → 领退料/工序执行 → 成品质检/入库 → 财务放行 → 发货/签收。

人员、客户、供应商、物料、仓库库位、工艺模板是主数据；工资由确认的工作记录汇总，不能成为生产事实的来源。采购到货不等于可用库存，工序完成不等于整单履约完成，填写授权人不等于已经审批。

建议实施顺序：

1. 正式使用前：岗位权限、欠款放行审批、工资冻结、关键审计与恢复演练。
2. 下一批：状态统一、历史门樘迁移、全部记录分页、BOM 未保存离开提示及并发版本冲突检查。
3. 再下一批：供应商应付/对账、实际材料与人工成本、退换/返工成本、经营统计；这些闭环需要单独业务验收，本轮没有证据证明其已具备完整财务账能力。

验收应至少包括多用户同时操作、防重复提交、越权拒绝、收款冲销、采购部分到货/退货、质检不合格、返工、订单变更、取消与库存释放、工资重审、备份恢复。财务正式账务在上述验收前继续使用已验证的账务流程。

本轮未修改上述审批和权限规则，也没有声称进行了完整公司 ERP 认证。
